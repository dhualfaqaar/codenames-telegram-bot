# التشغيل تحت الضغط وحصة الخطة المجانية

حصة Cloudflare تشمل الحساب كله، مو هذا البوت وحده. `100,000` كتابة صف يومياً ليست عدد مستخدمي تيليجرام، وطلبات Workers وDurable Objects لها حدود مستقلة. راجع [التسعير الرسمي](https://developers.cloudflare.com/durable-objects/platform/pricing/) و[حدود Workers](https://developers.cloudflare.com/workers/platform/limits/). ماكو ضمان أن الخدمة المجانية تكفي 100,000 مستخدم نشط أو ضغطاً متزامناً كبيراً.

النسخة الحالية تتفادى حفظ حالة البوت عند منشور قناة تم تجاهله، ولا تحفظ الحالة عند فحص متابعة الفرق إذا ماكو متابعة فعّالة. الحالات المتغيرة تبقى تنحفظ، ويُعاد طلب الحفظ عند فشل كتابة سابق ضمن نفس دورة حياة الكائن. هذا ما يعني أن كل الرسائل مجانية أو بلا كتابات، وما يحمي البيانات من فقدان كتابة فاشلة عند توقف الكائن قبل المحاولة التالية.

الاستيراد الجماعي للقناة يبقى متوقفاً؛ لا يُستأنف إلى أن نقيس تكلفة FTS ونبني استيراداً محدوداً وقابلاً للاستئناف. لم نقس استهلاك الحساب الفعلي أو نختبر 100,000 مستخدم على الإنتاج. بعد تجدد الحصة، قارن استخدام الحساب وMetrics لكل namespace بالأوقات نفسها، ثم نفذ اختبار حمل تدريجي خارج الإنتاج بسيناريوهات ألعاب وبحث واقعية، وراقب الأخطاء والكمون والكتابات والذاكرة والحدود.

معظم تحديثات تيليجرام وحالة البوت تستخدم Durable Object واحداً باسم `main` وتُحفظ في مفتاح واحد. هذا اختناق محتمل، وقيمة التخزين في SQLite-backed DO محدودة بحجم مفتاح وقيمة مجتمعين 2 MB بحسب [حدود Cloudflare](https://developers.cloudflare.com/durable-objects/platform/limits/). عند نمو المستخدمين يلزم تصميم توزيع الحالة والغرف تدريجياً مع خطة ترحيل ونسخ احتياطية واختبار استعادة؛ إنشاء كائنات أخرى لا يرفع الحصة اليومية المشتركة للحساب. لا تُقسَّم حالة البوت الفعلية أو تُنقل قبل اختبارات ترحيل تحافظ على البيانات. إرسال webhook الحالي يؤكد الاستلام قبل اكتمال معالجة التحديث، لذا فإعادة المحاولة وضمان عدم ضياع التحديثات عند الأعطال تحتاج تصميم مستقل، وليست مضمونة هنا.
